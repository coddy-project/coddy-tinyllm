# Cross-review: coddy-2bit-llm

## Findings

**1. The justification for a custom model is inverted — the plan's own baseline kills it. (Blocker)**
The plan says "the task is narrow, values are mostly booleans/ints/short enums, 208 fields, 4 verbs." That description is not "a task a small model is good at" — it is a task a rules engine is *designed* for. "выключи телеграм-гейтвей" is `disable <X>` where X is resolved by retrieval over 208 cards; "увеличь лимит ходов до 40" is `set <X>=40` with the number extracted by regex. The top-20 intents the plan itself lists (enable/disable, set N, change model, add MCP server) cover the overwhelming majority of real config requests, and each is a template with a retrieval slot. The M0 kill criterion ("within ~10 points of R1 → ship R0 and stop") is the right instinct, but it is set against the wrong comparison: R0 should be compared to *the model's expected value*, not to R1 (the frontier model). A frontier model with retrieval will be near-perfect on this task — it is a trivially easy task for it — so "within 10 points of R1" is a bar the rules engine will almost certainly clear, and the plan correctly concludes "stop." The problem is that the plan then proceeds to spend M1–M5 anyway, because the kill criterion only fires at M0 and the rest of the roadmap is written as if M0 will pass. **Recommendation:** restructure so M0 is not a milestone but a *gate*: if R0 ≥ 0.85 exact-match on the 300-example set, the project ends there and ships as a Coddy feature. Write the rules engine first, measure it against real session logs (donated sessions from 04-data), and only if the residual error distribution shows a clear, learnable pattern that rules cannot express (e.g., multi-clause instructions, cross-field constraints) does M1 start. The plan should state this explicitly: the default outcome is "ship R0, do not train anything."

**2. "Retrieve + constrain + train on mutated schemas" does not guarantee generalisation to unseen fields — it guarantees generalisation to unseen *values* of seen fields. (Major)**
The three mechanisms in §3.2 (schema randomisation, index-anchored supervision, grammar at inference) prevent the model from *memorising paths*. But they do not address the harder failure: **semantic mapping from instruction to field when the field is new**. If Coddy adds `swarm.rings[].fanout`, the model must understand that "make the swarm spread work to more agents" means `fanout`, not `replicas` or `workers`. The grammar constrains the *output space* to the retrieved candidates, but retrieval is what puts `fanout` in the candidate set in the first place. If retrieval fails (the alias file is stale, the description is terse, the user's phrasing is idiosyncratic), the model gets a candidate set that does not contain the right field, and the grammar then *prevents* it from emitting the correct one. The plan measures "unseen-field generalisation within 10 pts of seen fields" as a success criterion, but the mechanism that would achieve it — retrieval recall on new fields — is not in the model at all; it is in the alias file, which is regenerated per release by a frontier model. So the "no retraining" guarantee is actually "no retraining *of the model*, but the alias file must be regenerated and the retrieval must recall the new field." The plan should measure **retrieval recall@12 on fields added after the training cut** as a first-class metric, separate from model accuracy. If retrieval recall on new fields is 0.85, then even a perfect model caps at 0.85 on unseen fields. **Recommendation:** add a retrieval-recall metric for unseen fields to 06-eval, and treat the alias-file regeneration as a *release-blocking* step (like a schema migration), not an offline batch job that "degrades gracefully." A stale alias file silently degrades the system below the floor.

**3. The ternary track is not justified by the numbers the plan itself cites. (Major)**
The plan says ternary buys ~1.85× over Q4_0 on CPU and ~4× on memory, and that "the honest justification for track B is size — 60-80 MB is embeddable, 400 MB is not." But this is a non-sequitur. The question is not "can I embed the weights?" — it is "does the user benefit from embedding the weights?" A 400 MB model downloaded on first use into `~/.coddy/models/` is a perfectly normal pattern (it is what every Go-LLM project does). The user pays a one-time 400 MB download and gets a known-good, mature inference path. The user who gets a 60 MB embedded model pays the price of: (a) a ternary model that is *on par with the teacher on narrow tasks* — i.e., no quality benefit, and (b) a pure-Go inference runtime that the plan admits is "slower and is work we own." The 1.85× speedup is real but small; at the latency budget of 1.5 s for full generation, 1.85× takes it to ~0.8 s, which is still not "sub-second" in the way the problem statement promises. The plan's own latency table shows prefill is 300-800 ms of the 1.5 s budget; ternary does not help prefill much (it is still a matmul, just with fewer bits), so the realistic speedup is closer to 1.3-1.5× end-to-end. **Recommendation:** cut M5 entirely unless and until M2–M4 ship and the 400 MB download is demonstrably a user complaint. If the size objection is real, the cheaper fix is to quantise track A to Q3_K or use a smaller base (360 M variant from M2), which stays in the mature llama.cpp toolchain. The ternary track is a research project, not a product decision, and the plan should say so plainly.

**4. Hardware and cost estimates are plausible but the "$15" figure is misleading. (Minor)**
The $15 figure is for SFT of a 0.6B model on 20-50 k examples, which is correct for rented GPU time (a few hours on an A100). But the plan omits: (a) the cost of *generating* the 20-50 k training examples via a frontier model (backtranslation, mutation, verification) — this is not free and is not in the $15; (b) the cost of the alias-file generation per release (frontier model, 208 fields × 10 paraphrases × 2 languages = ~4000 calls per release, ongoing); (c) the cost of the evaluation harness running in CI (the plan says "the eval set running in CI" in M4, which means every PR pays GPU or CPU time for the 300-example set). The total program cost is more like $50-100 including data generation, not $15. This does not change the decision (it is still cheap), but the plan should not advertise "$15" as the program cost, because the reader will anchor on it and be surprised by the data-generation bill. **Recommendation:** break the cost into "one-time: $15 SFT + $X data generation" and "per-release: $Y alias regeneration + $Z CI eval." The data-generation cost is the one that scales with the number of schema changes.

**5. The no-op / abstention design is sound in principle but has a silent-failure mode the plan does not address. (Major)**
The plan says "a model that occasionally rewrites someone's config because they said 'make the tests run faster' is worse than no model." This is correct, and the no-op precision floor of 0.98 is the right metric. But the plan does not address what happens when the model is *confidently wrong in the other direction*: it emits a valid, schema-clean, dry-run-clean command set that is *semantically* wrong. The verifier (parse + dry-run + schema check) catches syntax and schema errors, but not semantic errors. "Make the tests run faster" → the model emits `set agent.max_turns=4` (valid, dry-runs clean, schema-valid) because it associated "faster" with "fewer turns." The operator sees the staged edit and must catch it. The plan relies on the operator's review as the last line of defense, which is fine for an explicit command (`coddy config "..."`) but dangerous for ambient mode, where the operator is not looking at a config diff. The plan says ambient mode ships "second and off by default," which mitigates this, but the no-op precision floor of 0.98 means 1 in 50 non-config turns produces a *plausible-looking* config edit that the operator must notice and reject. **Recommendation:** add a **semantic plausibility check** to the verifier: before staging, compute the "surprise" of the edit relative to the instruction (e.g., does the instruction contain a number that matches the value? does the field's description share tokens with the instruction?). If the surprise is high, flag the edit for explicit operator confirmation even in ambient mode. This is cheap (string overlap, number extraction) and catches the "make the tests run faster" → `max_turns=4` class of error. Without it, the 0.98 no-op precision floor is not enough for ambient use.

**6. The goccy/go-llama bet is the right risk to take, but the fallback is underspecified. (Major)**
The plan correctly identifies that M3 is a spike, not an adoption, and that the kill criterion is "if no cgo-free Go path meets the latency budget, ship behind a cgo sub-tag." This is sound. But the fallback is underspecified: "a cgo sub-tag for the people who want it" means the default build does not have the feature, which means the project's core value proposition (offline, no cloud, sub-second) is not available to the default user. The plan should state explicitly: **if M3 fails, the project ships as a developer-only feature and the "offline config editing" value proposition is not delivered to end users.** This is a significant scope reduction that the plan should acknowledge rather than bury in a kill criterion. The alternative fallback — writing a pure-Go inference runtime for a 0.6B model — is a multi-month project that the plan does not cost or schedule. **Recommendation:** add a third fallback to M3: if goccy/go-llama fails and cgo is unacceptable, the project ships the *retrieval + rules + grammar* pipeline (M0) as the product, and the neural component is deferred to a follow-up project with a dedicated inference runtime. This is the honest outcome and the plan should name it.

**7. What is missing from the plan entirely. (Major)**

- **Failure telemetry.** The plan has no plan for what happens when the model is wrong in production. There is no logging of no-op decisions, no logging of escalated requests, no way to measure the real-world no-op precision against the 0.98 floor. Without this, the system ships blind and the "it is allowed to be wrong, it is not allowed to be silently wrong" guarantee is unenforceable. **Recommendation:** add a structured log line for every gate decision (NOOP/EDIT, confidence, instruction hash, retrieved fields, emitted commands, verification result) and a weekly report that compares the logged no-op precision against the floor. This is the difference between a system that is safe and a system that is *known* to be safe.

- **The "already in that state" NOOP class is underspecified.** The plan lists three NOOP reason classes: "not about settings / already in that state / needs a human." The second class is the hardest: "выключи телеграм" when `gateways.telegram.enable` is already `false`. The model must read the current config value and decide that the instruction is already satisfied. This is a *comparison* task, not a *generation* task, and it is not obvious that a 0.6B model does it reliably. The plan should specify how this is handled: does the model see the current values in the prompt (yes, per §3.3)? Does the verifier check "is the target state already the current state?" (this is a cheap post-hoc check that should be in the verifier, not the model). **Recommendation:** move the "already in that state" check out of the model and into the verifier: after the model emits `set X=false`, the verifier checks if `X` is already `false` and, if so, converts the output to NOOP with reason "already in that state." This is deterministic, free, and removes the hardest NOOP class from the model's responsibility.

- **Multi-command instructions.** The plan's examples are single-intent ("увеличь лимит ходов до 40 и выключи телеграм" is two intents). The plan does not specify how the model handles instructions with 3+ intents, or how the grammar handles an arbitrary-length command list. The grammar in §3.3 is `program := (line "\n")* | "NOOP"`, which is unbounded, but the training data and the eval set should specify a maximum number of commands per instruction. If the model emits 10 commands for a 3-intent instruction, the verifier will catch the extras, but the operator's review burden scales with the number of commands. **Recommendation:** cap the number of commands per instruction at 5 in the grammar and in the training data, and treat "instruction with >5 intents" as an abstention/escalation. This bounds the operator's review burden and the model's output length.

- **The Russian/English bilingual aspect is a first-class requirement, not a footnote.** The plan mentions "Russian or English" in the problem statement and "bilingual lexicon" in the prefilter, but the data plan (04-data) and the training recipe (05-training) are not visible in this review. The base model (Qwen3-0.6B) is multilingual, but the *training data* must be bilingual, and the eval set must have a balanced Russian/English split. The plan should specify the language ratio in the training data and the eval set. If the training data is 80% English, the Russian no-op precision will be lower than the 0.98 floor, and the plan will not know until it measures it. **Recommendation:** specify a 50/50 or 60/40 Russian/English split in the training data and a separate Russian-only and English-only eval slice, with the no-op precision floor applied to each slice independently.

## Verdict

**Build a reduced version.** The project as written is a research programme with a product buried in it. The product is M0: a retrieval + rules + grammar pipeline that handles the top-20 intents with no neural network, ships in Coddy behind a build tag, and costs nothing to run. This is the 80% of the value at 10% of the cost and 0% of the risk. Build M0, ship it, measure it against real session logs, and let the residual error distribution tell you whether a model is needed.

Cut: M5 (ternary) entirely — it is a research project, not a product decision, and the plan's own numbers do not justify it. Cut: the "ambient mode" from the initial scope — ship explicit-only (`coddy config "..."`) and defer ambient mode until the no-op telemetry from real use justifies it. Cut: the "under $15" cost framing — it is misleading and the data-generation cost is the real bill.

Keep: M0 (the rules engine, the retrieval, the eval harness), M1 (the data engine, but only if M0's residual errors are learnable), M2 (the SFT, but only if M1's ceiling is high enough), M3 (the Go runtime spike, but with the honest fallback that "if this fails, the product is M0"). The plan's architecture (§3) is sound and the "model learns intent, not schema" principle is correct. The plan's *sequencing* is wrong: it treats the model as the product and the rules engine as the baseline, when the rules engine is the product and the model is the optional optimisation.

The one-sentence summary: **the plan is a well-researched justification for building a rules engine that is dressed up as a machine-learning project, and the rules engine is the part that should ship.**
