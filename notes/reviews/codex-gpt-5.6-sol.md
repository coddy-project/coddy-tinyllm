1. **Blocker — The plan has not yet justified training a custom model because it omits the most important baseline: an unmodified Qwen3 model with retrieval and constrained decoding.** R1 uses a frontier model and R2 uses the fine-tuned model, leaving no measurement of Qwen3-0.6B-Q4 or Qwen3-1.7B-Q4 with the exact production prompt, cards, and grammar. The deterministic baseline is also probably too weak: “about twenty rules” risks becoming a straw man when a compositional parser can handle direct paths, booleans, numbers, units, aliases, and ambiguity without one rule per field. **Recommendation:** add R0.5 for a serious deterministic semantic parser, R0.6 for stock Qwen3-0.6B, and R0.7 for stock Qwen3-1.7B. Do not generate 50,000 examples unless fine-tuning materially improves selective accuracy over stock 0.6B—not merely raw exact match.

2. **Blocker — The observed demand is too small to support the product case as written.** Only 10 of 111 sessions even mention `config_set`, so a 100–400 MB artifact, a new runtime, training infrastructure, and six-platform maintenance may be optimizing an operation users perform monthly. Offline availability is a legitimate benefit, but the plan never estimates requests per active user, frontier-call cost actually avoided, download amortization, or the number of users who need offline config editing. **Recommendation:** measure genuine config-edit frequency and run an explicit-command prototype first; define a minimum adoption and avoided-latency threshold before authorizing model work.

3. **Major — Schema retrieval and mutation provide syntactic forward compatibility, not reliable semantic generalization to genuinely new fields.** A model can choose an unfamiliar path only when the request, description, and learned concepts align. It will fail on new semantic domains, unfamiliar units, cross-field behavior, conditional settings, renamed concepts, poor descriptions, or fields requiring operations absent from its training taxonomy. Mechanical renaming mostly tests resistance to path memorization; it does not simulate learning a novel concept from a card. **Recommendation:** weaken “works on day one” to “can address new fields without retraining,” hold out entire semantic families and schema structures, run historical forward-chaining tests across real Coddy releases, and retrieve parent descriptions, constraints, related fields, and examples—not just isolated leaf cards.

4. **Major — The grammar guarantees are overstated.** A trie over paths and coarse types can prevent unknown leaf names and malformed primitive syntax, but it cannot by itself guarantee schema validity: ranges, regexes, formats, nullability, unions, conditional constraints, quoting rules, map keys, list element structure, and cross-field invariants remain. Selector-addressed paths are especially unresolved: `mcp_servers[name=context7]` contains a dynamic selector value that is neither a static schema path nor a simple typed value. **Recommendation:** claim only syntax and candidate-path containment, specify the concrete-path expansion algorithm for lists and maps, and build schema-compiler conformance tests covering every schema construct before treating grammar validity as an invariant.

5. **Blocker — The no-op metric is backwards for the dangerous failure mode.** If NOOP is the positive class, editing a non-config turn is a NOOP false negative and therefore damages NOOP recall, not NOOP precision. The stated recall floor of 0.90 could permit edits on 10% of true no-op turns, while even the 0.995 target corresponds to an unacceptable ambient failure rate if interpreted as one unsafe decision per hundreds of turns. **Recommendation:** report `false_edit_rate = P(EDIT | non-config)`, edit precision, and risk-versus-coverage curves. Ambient deployment should require a statistically supported false-edit upper bound closer to \(10^{-4}\) or better; demonstrating that with zero observed failures requires roughly 30,000 representative negative turns for a 95% upper bound near \(10^{-4}\).

6. **Blocker — Staging an ambient suggestion is not protection against silent corruption.** Valid-but-wrong edits pass every verifier, and an unintended edit can remain in a shared staging area until a later `config_commit` commits it alongside legitimate work. “Shown to the operator” is also weak protection against confirmation fatigue. **Recommendation:** ambient mode must never mutate shared staging state. Produce an isolated, expiring proposal with the source turn, base-config hash, exact diff, and transaction ID; stage it only after explicit acceptance, then reject it if the config changed meanwhile.

7. **Major — NOOP, abstention, and routing are conflated despite requiring different control flow.** “Not about settings” should return control to the agent; “already in that state” should complete without an edit; “ambiguous” should ask or escalate; and “unsupported” should use the normal LLM. The gate cannot identify “already set” before retrieval and reading current values, while the grammar exposes only a bare `NOOP`, contradicting the promised reason classes. Retrying parser-valid generation does nothing for semantic errors. **Recommendation:** define distinct terminal states such as `NOT_CONFIG`, `ALREADY_SATISFIED`, `AMBIGUOUS`, `UNSUPPORTED`, and `EDIT`; derive confidence externally from calibrated scores and retrieval/OOD signals rather than trusting a self-reported token.

8. **Major — The evaluation sets are too synthetic and too small to establish ambient safety.** Changing the teacher does not remove generator-style artifacts, and 100–300 donated cases cannot support a 0.995 safety claim or useful bilingual subgroup estimates. A future release is also unavailable when deciding whether the first model may ship. **Recommendation:** add human-written blinded evaluation, shadow-mode production traffic, confidence intervals, per-field and per-operation risk, and acceptance/rejection telemetry. Use historical releases as temporal splits now, reserve the next real release as post-ship confirmation, and evaluate the complete prefilter→gate→retriever→generator pipeline rather than each favorable component separately.

9. **Major — The proposed log labels are noisy and the redaction plan is incomplete.** “No `config_set` occurred” does not mean “the turn was not a config request”; the agent may have missed the intent, used another path, failed, or been interrupted. `RedactedString` also does not establish that instructions, arbitrary string values, MCP arguments, hostnames, repository names, paths, and config structure are safe to publish under a permissive license. **Recommendation:** treat session negatives as positive-unlabeled data, manually audit stratified samples, and design a field-aware export threat model with local review, provenance, consent, and tests using planted secrets.

10. **Major — The ternary track is an unjustified product bet at a measured 1.85× speedup.** The work includes unreleased distillation reproduction, a new weight format, bespoke kernels, tokenizer integration, and permanent cross-platform runtime ownership. Ternary matmul is not the whole inference workload: unpacking, activations, attention, normalization, embeddings, KV state, grammar masking, and memory bandwidth remain. The memory claim is also optimistic: ideal 1.58-bit versus ideal 4-bit storage is about 2.5×, not 4×, and a 0.6B model alone has a theoretical 118 MB ternary weight floor before scales, tokenizer, metadata, and potentially higher-precision embeddings. **Recommendation:** remove ternary from the product roadmap and retain it as a separate research experiment only if a deployed Q4 model has demonstrated demand and misses a measured hard size or latency requirement.

11. **Major — Several cost statements contradict either the arithmetic or one another.** The SFT FLOP calculations are internally reasonable, but “the whole programme is under $15” excludes the later stated $150–400 data bill, experiment retries, hyperparameter sweeps, failed runs, storage, and engineering. For rejection sampling, 50,000 prompts × 8 × 30 completion tokens is about 12 million output tokens, not 400 million; roughly 480 million prompt-token evaluations arise only if the 1,200-token prefix is repeatedly processed without reuse. Conversely, the claim that 100B-token ternary training takes a week on eight H100s conflicts with the quoted 380 TFLOP/s each: the provided FLOP formula gives roughly 14 hours at that effective throughput, while the stated ~$205 cost also corresponds to hours, not a week. **Recommendation:** publish separate low/expected/high estimates for data generation, training, evaluation sweeps, ternary work, and engineering; specify batching, prefix reuse, MFU, model API prices, and GRPO rollout parameters.

12. **Blocker — Depending on a three-month-old wasm-to-Go transpilation project is too risky for the primary runtime.** The project must simultaneously provide numerical correctness, tokenizer parity, grammar callbacks, mmap or efficient loading, SIMD performance, bounded allocations, cancellation, threading, Windows/macOS/Linux behavior, and sustainable synchronization with llama.cpp. Generated Go source does not automatically preserve llama.cpp’s performance characteristics, and owning the fork could cost more than the model project. **Recommendation:** move the runtime spike before large-scale data generation and SFT. Define the production fallback now: an optional, checksummed per-platform llama.cpp runner invoked as a subprocess, a cgo build-tag implementation, or connection to a user-supplied `llama-server`; keep the normal LLM and deterministic R0 paths when none is installed.

13. **Major — The latency and artifact budgets are assumptions, not a plausible commitment for the proposed default path.** The estimates appear closer to optimized native kernels than an unproven pure-Go runtime, especially on the i7-8750H and arm64. They omit model load/cold start, mmap behavior, tokenizer cost, grammar-mask overhead, concurrent HTTP requests, CPU contention with Coddy itself, and Russian prompts with less favorable tokenization. The 100 MB target is incompatible with Qwen3-0.6B even at ideal 1.58-bit storage. **Recommendation:** benchmark stock Q4 weights through the intended runtime on all three reference machines before training, report cold/warm and concurrent p50/p95, and make model download plus memory mapping the default packaging assumption.

14. **Major — The plan is missing a compatibility and operations design.** There is no model/runtime/tokenizer/schema compatibility manifest, signed model-update mechanism, rollback policy, cache eviction policy, corruption recovery, memory ceiling, concurrency model, cancellation behavior, or response to a model becoming incompatible with a newer grammar compiler. There is also no treatment of config changing between inference and acceptance. **Recommendation:** version the model, tokenizer, grammar ABI, card format, and minimum/maximum schema versions together; verify checksums or signatures; use compare-and-swap against the input config hash; and specify resource limits and update rollback before integration.

15. **Major — The security model covers schema validity but not adversarial semantic input.** Current config strings and user instructions can contain delimiter-like text, command-looking content, hostile MCP names, secret literals, or values designed to manipulate generation. Grammar restriction limits the damage surface but still allows choosing any retrieved valid field and dangerous valid value. Credential handling is policy, not merely a learned preference. **Recommendation:** serialize inputs with unambiguous escaping, keep secrets entirely out of model context where possible, enforce credential and high-risk-field policies in deterministic code, and require stronger confirmation for network exposure, executable paths, commands, provider endpoints, and credentials.

16. **Minor — SFT plus verification is sensible, but rejection sampling and GRPO are prematurely treated as expected stages.** The verifier proves applicability, not correspondence to user intent, except on synthetic cases where a gold post-config is already available. Partial rewards for parsing and validity can encourage confidently wrong but valid edits, and the claimed GRPO gains have no task-specific basis. “Packing off preserves prompt structure” is also not generally true; masked, boundary-aware packing can retain structure while improving throughput. **Recommendation:** stop after SFT unless a controlled ablation shows rejection sampling or RL improves calibrated selective accuracy on human-written data; prefer supervised hard negatives and error-driven data generation first.

17. **Minor — The core choice of a small edit DSL, live-schema retrieval, deterministic parsing/dry-run, and explicit-first deployment is sound.** Those components sharply reduce the output surface and are independently useful even if every neural experiment fails. The M0 kill criterion and optional build tag are also directionally correct, although the thresholds need cost-sensitive justification. **Recommendation:** preserve those parts and design them as a complete deterministic feature rather than scaffolding that only becomes useful once a model exists.

**Verdict:** build a reduced version. Build the production-grade retriever, compositional rules parser, schema/grammar compiler, verifier-backed proposal object, evaluation harness, and explicit `coddy config "…"` entry point; add stock Qwen3-0.6B and 1.7B prompt-and-grammar baselines and perform the runtime spike immediately. Fine-tune 0.6B only if it materially beats both deterministic parsing and stock Qwen on human-written, temporally split data at a useful selective coverage. Ship any model as an optional downloaded asset through a mature native runner or cgo-tagged implementation. Cut ambient staging, the custom gate model, GRPO, embedded weights, and the entire ternary product track until real usage and measurements demonstrate that they solve an actual bottleneck.
